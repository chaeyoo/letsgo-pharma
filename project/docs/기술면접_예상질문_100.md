# 기술면접 예상 질문 100선 — RAPV-Assistant

> 레포의 문서(`README.md`·`description/아키텍처.md`·`docs/면접노트.md`), 실제 코드(`src/`),
> 발표자료(AX풀스택 AI엔지니어 지원 PDF)를 근거로 정리한 기술면접 예상 질문 100개와 두괄식 답변.
> 답변은 **결론 먼저(3~4줄)** 형식이며, 상세 근거는 각 정본 문서와 코드 위치를 함께 표기했다.

---

## A. 프로젝트 개요·문제정의 (Q1~Q8)

### Q1. 이 프로젝트를 한 문장으로 소개한다면?
**A.** 제약 규제업무(RA·PV) 담당자의 규정 검색부터 이상사례 트리아지→인과성→코딩→보고서 초안까지를
RAG + MCP 에이전트로 자동화한, **평가(신뢰구간 포함)와 CI로 뒷받침되는 작동 데모**입니다.
공고 필수 스택(RAG 최적화·Agentic Workflow·Function Calling·MCP/FastMCP·FastAPI)을 한 프로젝트로 증명하며,
근거·버전 추적, PII 마스킹, 사후 검증 게이트까지 규제 도메인의 신뢰 요건을 응답 구조에 박았습니다.

### Q2. 왜 하필 RA·PV 도메인을 골랐나?
**A.** "LLM 신뢰성 문제가 가장 첨예한 도메인"이기 때문입니다 — 문서가 많고(답은 고시·SOP 어딘가에),
업무가 반복되며(접수→판정→기한 계산→보고), 틀리면 곧바로 컴플라이언스 사고입니다.
그래서 환각 있는 LLM을 그대로 쓸 수 없고, 이를 믿을 수 있게 만드는 엔지니어링이 핵심 과제가 됩니다.
RA(규제문서 검색+마감·체크리스트)와 PV(케이스 처리 워크플로) 두 도메인을 대칭으로 다룹니다.

### Q3. "LLM을 어떻게 믿을 수 있게 만들 것인가"에 대한 이 프로젝트의 답은?
**A.** **신뢰의 경계선 3개**입니다 — ① 들어오는 경계: PII를 에이전트 입구+도구 계층 2겹에서 마스킹,
② 가운데 경계: 판정·기한 계산은 결정론 규칙, LLM은 도구 선택·설명만(모델과 도구는 MCP로 분리),
③ 나가는 경계: 모든 답에 출처 부착, 근거 약하면 회피(abstention), 나가는 수치·날짜·방향은 검증 게이트가 근거와 대조.
여기에 시간축이 겹칩니다 — 배포 전엔 preflight가 차단하고, 운영 중엔 경고율 계기판이 감시합니다.

### Q4. 이 시스템이 실제로 해주는 일은?
**A.** 크게 넷입니다 — ① 규정 질문에 근거+출처(문서·섹션·버전) 답변(RAG), ② 케이스 서술로
중대성 판정·보고기한 계산·인과성 제안·용어 코딩(`assess_adverse_event`), ③ ICH E2D 최소보고요건을
검증한 KAERS 보고서 초안(`draft_ae_report`), ④ 마감일 D-day·제출 체크리스트 조회입니다.
복합 질문("GMP 변경인데 뭘 준비하고 언제까지?")은 에이전트가 도구를 연쇄 호출해 종합합니다.

### Q5. GC녹십자 Hey.GC 2.0과는 어떤 관련이 있나?
**A.** 같은 구조 원리를 씁니다 — Agentic AI가 MCP 규격으로 사내 시스템(도구)을 호출하는 구조입니다.
도구를 에이전트 코드에 함수로 박지 않고 별도 MCP 서버로 분리했기 때문에, 자체 에이전트와
Claude Desktop이 **같은 서버의 같은 도구**를 호출하고, 새 사내 시스템은 도구 추가로 끝납니다.
N×M 통합이 N+M으로 줄어드는 확장성 원리를 데모 규모에서 실증한 것입니다.

### Q6. 규제 수치가 실제 법령과 다르면 문제 아닌가?
**A.** 데모용 가상 샘플임을 문서마다 명시했습니다 — 각 규제문서 frontmatter에 disclaimer가 있고,
기한 체계(사망·생명위협 즉시, 그 외 중대 15일)는 자작 규정 REG-005 기준이라 실제 ICH E2A와 다릅니다.
목적이 규제 자문이 아니라 **아키텍처·엔지니어링 역량 증명**이므로, 실배치 시 실 규정 코퍼스와
현업 검증 라벨로 교체하면 같은 파이프라인·평가 하네스가 그대로 쓰입니다.

### Q7. 이 프로젝트가 FDE(Forward Deployed Engineer) 역량을 증명하는 방식은?
**A.** FDE의 일 — 문제 정의→설계·개발·배포→성과 측정 — 을 실제로 한 바퀴 돌았습니다.
현업(RA·PV)의 반복 업무에서 시작해, 데이터→RAG→MCP→에이전트→API→UI→평가→CI 전 구간을 혼자 연결했고,
모든 주장을 재현 가능한 수치(95% CI 병기)로 기록했습니다. 모델 학습은 의도적으로 범위 밖이며,
기성 LLM을 현업 워크플로에 신뢰 가능하게 배치하는 통합 역량이 초점입니다.

### Q8. 프로젝트에서 가장 어려웠던 문제는?
**A.** "다 만든 뒤"가 진짜 시작이었습니다 — 테스트가 초록이고 지표가 1.0인 상태에서 숨은 결함
(마스킹 우회 경로, 검증 축 비대칭, as_of 조합 결함)을 찾는 적대적 재점검(v6~v12)이 가장 어려웠습니다.
"이 부분이 고장 나면 누가 알아차리는가"라는 질문으로 조용한 실패 경로를 체계적으로 수색했고,
그 판정 기준 자체(논리적 비약 4형태·사각지대 탐색 4절차)를 문서로 명문화해 재사용 가능하게 했습니다.

## B. 아키텍처·설계 원칙 (Q9~Q16)

### Q9. 요청 하나가 흐르는 전체 경로를 설명해달라.
**A.** 웹 챗 UI → FastAPI `/chat` → **PII 마스킹(에이전트 입구)** → 에이전트(키 있으면 LLM tool-use 루프,
없으면 규칙 라우팅) → **MCP 프로토콜(HTTP)로 FastMCP 서버의 도구 호출** → RAG 검색 / PV 규칙 워크플로 /
RA 업무 데이터 → **답변 사후 검증 게이트**(수치·날짜·방향·역할 ↔ 근거 대조) → 답변+출처+도구
트레이스+검증 배지로 반환됩니다. 관측성 계층이 전 스텝을 span으로 계측합니다.

### Q10. LLM 모드와 오프라인 모드의 차이는?
**A.** 차이는 "누가 도구를 고르는가"뿐입니다 — LLM 모드는 Claude가 tool-use로 스스로 선택하고,
오프라인 모드는 규칙 라우터(`_route_intent`)가 분기합니다. 두 모드는 **동일한 MCP 도구, 동일한
인터페이스, 동일한 사후 검증 게이트**를 쓰므로 API 키가 없어도 전 기능이 동작합니다(graceful degradation).
단, 회피 판정 방식은 명시적으로 다릅니다 — 문턱 기반 abstention은 오프라인 검색 경로 전용입니다.

### Q11. LLM과 규칙 코드의 역할 분담 기준은?
**A.** "규정이 정한 계산은 결정론, 이해·조합은 LLM"입니다. 보고기한·중대성·최소보고요건은
컴플라이언스 그 자체라 하루 틀리면 사고인데 LLM의 날짜 연산은 확률적이라 감사를 통과할 수 없습니다.
그래서 판정·계산은 같은 입력에 항상 같은 출력을 내는 규칙 도구가 맡고, LLM은 자연어 이해·도구
선택·결과 종합 설명(orchestration)을 맡습니다. 이 경계 설계가 엔터프라이즈 에이전트의 핵심이라고 봅니다.

### Q12. "조용한 실패 금지"란 구체적으로 무엇인가?
**A.** 실패가 신호 없이 그럴듯한 답으로 포장되는 경로를 없애는 규율입니다. 미지원 카테고리·형식
틀린 `as_of`·빈 질의에 빈 목록 대신 `{"error", "available"/"expected"}` 명시적 에러 계약을 반환하고
(빈 결과는 "임박한 마감 없음"이라는 자신 있는 오답이 됨), 도구 예외는 `is_error`로 모델에 되먹여
자가복구를 유도하며, 폴백(인지일 형식 오류→오늘)은 반드시 caveat를 붙입니다. LLM API 실패도
오프라인으로 조용히 강등하지 않고 명시적으로 실패를 안내합니다.

### Q13. preflight(차단)와 검증 게이트(경고)의 실패 방향이 다른 이유는?
**A.** **시점에 따라 옳은 실패 방향이 다르기 때문**입니다. 배포 전엔 아직 사용자가 없어 시끄럽게
멈추는 비용이 0이고 조용히 뜬 결함 서버의 비용이 크므로 preflight는 실패 시 exit 1로 기동을 차단합니다.
운영 중엔 검증기 자신도 오탐 가능성이 있어 자동 차단하면 정당한 답변이 죽으므로, 게이트는 차단이
아니라 경고 부착(본문·API·UI 3곳 노출)으로 사람의 최종 확정을 빠르게 합니다.

### Q14. 실서비스 전환 시 교체 지점은 어디에 있나?
**A.** 전부 인터페이스·대체 구현으로 **코드에 이미 존재**합니다 — 임베더는 `EmbeddingProvider`
프로토콜(Voyage API 경로 실증), 리랭커는 `_rerank_score`(Cross-Encoder 자리), 벡터스토어는
`InMemoryVectorStore`(pgvector 자리), PII는 `redactor.py`(Presidio 등 NER 자리), 코딩 사전은 MedDRA
본체 교체 자리, 문서 인제스트는 `scripts/ingest_pdf.py`(PDF→코퍼스 변환 실코드), 인증은 FastAPI
미들웨어 자리입니다. "확장 지점이 말이 아니라 코드로 존재"하는 것이 포인트입니다.

### Q15. 의도적으로 범위에서 뺀 것은?
**A.** 실제 Vector DB(인메모리로 대체 — 개념 동일·배포 단순), 상용 임베딩·리랭커(순수 파이썬 근사 +
실 API 경로만 코드로 표시), 인증·영속 DB(MVP 범위 밖)입니다. 반면 **CI는 포함**했습니다 —
테스트·평가 회귀는 확장 기능이 아니라 신뢰성의 기본이라고 판단했기 때문입니다.
원칙은 "완벽함보다 작동+설명"이며, 뺀 것도 교체 지점을 코드에 명시해 두었습니다.

### Q16. 인덱싱과 질의를 왜 분리했나?
**A.** 무거운 작업(frontmatter 파싱·청킹·IDF 학습·임베딩)은 서버 부팅 시 1회만 수행하고, 요청
경로에는 가벼운 검색만 남기는 **두 개의 시간축** 설계입니다. 그래서 검색 지연이 어휘 벡터 기준
~0.9ms 수준으로 유지됩니다. 실무에서 인덱싱은 배치 파이프라인, 질의는 온라인 서빙으로 분리되는
구조와 동일한 원리를 데모 규모로 구현한 것입니다.

## C. RAG 파이프라인 (Q17~Q36)

### Q17. 왜 벡터 검색만으로는 부족한가?
**A.** 실패 모드가 두 가지라서입니다 — ① 어휘 불일치(사용자는 "부작용", 문서는 "이상사례")와
② 하드네거티브(어휘가 겹치는 오답 문서 — 의약품 질문에 의료기기 규정). 전자는 도메인 동의어
질의확장이, 후자는 4신호 리랭킹+섹션 타입 prior가 해결합니다. BM25는 밀집 모델이 약한
고유명사·코드(DMF, ALCOA, 미등재 신약명) 정확 매칭의 보험으로 하이브리드에 남습니다.

### Q18. 하이브리드 검색의 결합 방식과 α=0.4의 근거는?
**A.** 벡터 코사인과 BM25 점수를 각각 min-max 정규화한 뒤 `α·벡터 + (1-α)·BM25`로 결합해 top 8을
회수합니다. α=0.4는 스윕 근거입니다 — TF-IDF 시절엔 0.3~0.7 전 구간 둔감해 중립값 0.5였으나,
e5 밀집임베딩 전환 후엔 0.5에서 의미 인접 이웃 문서 1건이 역전(Hit@1 0.969)하고 0.3~0.4에서
1.000이라, 벡터 신호가 강해진 만큼 가중을 낮춘 0.4를 채택했습니다(`config.py`에 근거 주석).

### Q19. 왜 min-max 정규화가 필요한가?
**A.** 두 점수의 스케일이 다르기 때문입니다 — 코사인은 0~1이지만 BM25는 상한이 없어, 그대로
더하면 한쪽이 결합을 지배합니다. 정규화는 **후보군 안에서** 수행해야 스케일이 왜곡되지 않으며,
버전 필터를 통과한 후보들에 대해서만 정규화하도록 구현했습니다(`retriever._hybrid`).
단, 무신호 판정은 정규화 전 원점수 기준입니다 — min-max는 '전원 동점'을 전원 0으로 만들기 때문입니다.

### Q20. 청킹 전략은? overlap은 왜 두나?
**A.** 문서의 헤딩 구조 기반 분할에 500자 청크/80자 overlap을 씁니다(`chunker.py`).
overlap은 청크 경계에 걸린 문장의 정보 유실을 막는 장치입니다. 각 청크에는 "[제목 > 섹션]"
컨텍스트 prefix와 문서 메타(doc_id·version·effective_date·status)가 붙어 출처 추적과
버전 필터의 단위가 됩니다. 설정 조합의 모순(overlap ≥ chunk_size)은 preflight가 기동 전에 잡습니다.

### Q21. 임베딩 구성은 어떻게 되나?
**A.** `EmbeddingProvider` 프로토콜 하나에 4개 구현입니다 — 기본은 밀집임베딩
`multilingual-e5-small`(query:/passage: 비대칭 prefix, 로컬 실행), 미설치 환경은 TF-IDF 자동 폴백,
그 외 HashingEmbedder(해싱 트릭·OOV 강함)와 VoyageEmbedder(상용 API 경로 증명)가 있습니다.
`EMBEDDER_KIND=auto`가 환경을 감지해 폴백하므로 torch 없는 컨테이너에서도 데모가 항상 돌고,
무엇이 잡혔는지는 preflight가 기동 시 보고합니다.

### Q22. 밀집임베딩 전환의 이득과 비용은?
**A.** 이득은 **벡터 단독 축**에서 가장 뚜렷합니다 — 하드네거티브 Hit@1 0.786→1.000,
ContextRecall 0.781→0.969. 임베딩 개선과 리랭킹이 각자 다른 실패 모드를 막는 이중 방어가 됩니다.
비용은 지연입니다 — 어휘 벡터 0.4ms → 밀집 인코딩 십수 ms. 의미 매칭을 얻는 대신 치르는
비용임을 수치로 함께 기록했습니다(면접노트 3장 표).

### Q23. 리랭커의 4신호는 무엇이고 왜 그 구성인가?
**A.** coverage 0.55(본문 질의 토큰 커버리지, idf^p 가중) + phrase 0.20(정확 구문 매칭) +
section 0.15(섹션 제목 매칭 — 같은 문서 안 정답 섹션 선택) + title 0.10(문서 제목 정합 —
하드네거티브 반증 신호)의 가중합입니다. 섹션과 제목을 **별도 필드 신호로 분리**한 것이 핵심인데
(BM25F 감각), 섞으면 같은 문서의 모든 청크가 제목 토큰을 공유해 섹션 간 변별이 죽기 때문입니다.
가중은 수치 최적화가 아니라 신호의 역할 분리 기준으로 고정했습니다.

### Q24. 섹션 타입 prior란 무엇인가?
**A.** 본문 어휘로는 못 거르는 구조적 실패를 섹션 '제목'의 패턴으로 잡는 신호입니다 —
대조 섹션("~와의 차이/구분")은 상대 도메인 어휘를 통째로 인용해 coverage가 정답을 이기므로
질의가 비교를 묻지 않을 때만 0.3 감점, 서두 섹션(목적/개요/총칙)은 주제 어휘를 요약해 담아
과대평가되므로 0.055 감쇠합니다. **질의 의도 게이트**가 핵심입니다 — 사용자가 정말 "차이"를 물으면
대조 섹션이 곧 정답이라 페널티가 꺼지며, 그 게이트 검증 문항을 평가셋에 추가해 두었습니다.

### Q25. 리랭킹 후에도 1차 점수를 섞는(rerank_weight=0.9) 이유는?
**A.** 순수 재정렬(1.0)은 쉬운 질의를 오히려 떨어뜨렸기 때문입니다(초기 Hit@1 0.833).
1차 하이브리드 점수를 10% prior로 결합하니 안정화됐고, 이는 실무 Cross-Encoder 리랭커도
first-stage 점수와 결합하는 관행의 반영입니다. 스윕 결과 밀집임베딩 전환 후엔 0.7~0.9가
플랫(1.000)이고 1.0만 1건을 잃어 0.9를 유지했습니다 — 감이 아니라 `eval/sweep.py`로 재현되는 값입니다.

### Q26. 질의확장은 어떻게 설계했나?
**A.** 도메인 동의어 사전(구어→정식 용어, **단방향 append**)으로 확장하되, **1단계 회수에는 전 가중,
2단계 리랭킹에는 확장 토큰을 절반 가중의 보조 신호로만** 반영합니다 — 회수(recall)와 정밀(precision)의
역할 분리입니다. 이 보조 신호는 ablation으로 존재 이유를 증명했습니다: prior를 끄면(rerank_weight=1.0)
aux 유무가 Hit@1 0.969 vs 0.906을 가릅니다. 단방향인 이유는 양방향·연쇄 확장이 노이즈를
지수적으로 만들기 때문입니다 — 원 질의는 항상 보존됩니다.

### Q27. 왜 LLM 질의 재작성(query rewriting)이 아니라 사전인가?
**A.** 결정론(같은 질의=같은 확장, 감사 가능)·저지연·무비용이기 때문입니다. 규제 도메인 용어는
변화가 느리고 유한해 사전이 잘 맞고, 밀집임베딩과도 상보적입니다 — 도메인 고유의 구어↔정식 용어
대응은 사전이 더 결정적·설명 가능하게 잡습니다. 실무에선 사전을 현업 용어집·SOP에서 추출해
관리하고, 사전이 못 메우는 롱테일에만 LLM 재작성을 얹는 하이브리드가 비용 대비 효과적입니다.

### Q28. 질의확장이 오히려 검색을 망친 사례는?
**A.** 있었고, 그래서 뺐습니다 — "DMF→원료의약품 등록" 확장이 정의 섹션(개요)으로 주제 표류를
일으켜 ContextRecall을 떨어뜨렸습니다. 문서가 이미 약어를 병기하는 용어는 확장이 불필요하다는
교훈을 얻었고, eval로 확인 후 사전에서 제거했습니다. "사전 한 줄도 감으로 넣지 않고 eval로
검증한다"가 이 프로젝트의 일관된 방법론입니다.

### Q29. 버전 인지 검색이란? 왜 중요한가?
**A.** 규제문서에 `version`·`effective_date`·`status(active/superseded)` 메타를 두고 **폐지 구판은
기본 검색에서 제외**하는 것입니다 — 규제는 개정이 잦고, 폐지된 옛 기준 인용은 그 자체가 사고입니다.
이력 조회는 `include_superseded`, 과거 시점 조회는 `as_of`로 명시적으로만 엽니다.
데모 코퍼스에 구판 REG-013(30일)과 현행 REG-005(15일)의 기한 충돌을 일부러 심어, 기본 검색은
현행만·이력 조회 시 구판 노출을 테스트로 보증합니다.

### Q30. as_of(시점 조회)에서 발견한 조합 결함은?
**A.** '폐지본 기본 제외'를 as_of에 그대로 겹치면, 개정된 규정은 과거 시점 조회에서 구판(폐지
필터)과 신판(당시 시행 전)이 **모두 걸러져 0건**이 되는 결함입니다 — 각 필터의 단위 테스트는
통과하는 조합 결함이라 발견이 어려웠습니다. 수정은 '당시 현행' 구간 판정([시행일, 후속본 시행일))
이고, 시행일 해석 불가 문서는 fail-closed로 제외하되 데이터 결함 자체는 preflight가 보고합니다.
이 의미론의 전제(폐지 체인 시행일 단조성)도 preflight가 기동 전에 검사합니다.

### Q31. 기본 검색이 as_of=오늘과 동치라는 건 무슨 의미인가?
**A.** v9에서 경로를 통일한 결과입니다 — 종전 기본 검색은 status만 보고 시행일을 안 봐서, 미래
시행일 active 문서가 '오늘의 현행'처럼 반환되고 그 시행 중 구판은 폐지 필터에 걸리는 잠복 결함이
있었습니다. as_of 경로에서 봉합한 결함과 동형이 무 as_of 경로에 남아 있던 것이라, 두 경로를
하나의 구간 판정으로 통일해 **코드 갈래 자체를 줄였습니다**(같은 결함이 갈래마다 재발하지 않도록).
'시행 중 구판 부재' 데이터 결함은 preflight가 잡습니다.

### Q32. 무신호 질의 처리 계약은?
**A.** 전 후보의 벡터·BM25 원점수가 모두 바닥이면 **빈 결과**를 반환합니다 — 안정 정렬이 전부
0점인 후보를 코퍼스 첫 문서 순서대로 내보내 '가짜 순위'가 되는 것을 막는 계약입니다(v9).
밀집임베딩은 무관 질의에도 0.3~0.6대 코사인이 나와 '0 이하=무신호'가 성립하지 않으므로,
provider별 바닥값(`DENSE_SIGNAL_FLOOR=0.835`, 실측 분포 기반)으로 일반화했습니다(v13).
MCP 도구 계층은 빈 질의를 빈 결과가 아니라 명시적 에러 계약으로 답합니다.

### Q33. 하드네거티브 평가는 왜, 어떻게 설계했나?
**A.** 초기 코퍼스(6문서)는 너무 작아 벡터/하이브리드/리랭킹 수치가 전부 동일(0.875)했습니다 —
"최적화 효과"를 증명할 수 없는 상태였죠. 그래서 어휘는 겹치지만 정답이 다른 **하드네거티브 문서
7종**(의약품↔의료기기 품목허가, 의약품↔화장품 표시, GMP 데이터완전성↔실태조사 등)을 일부러
추가해 파이프라인 단계별 차이가 측정되게 만들었습니다. 평가셋 설계가 곧 최적화 스토리의
전제라는 것 — "평가가 곧 실력"이 이 장의 요지입니다.

### Q34. 하이브리드가 벡터 단독보다 Hit@1이 낮은데(0.844 vs 0.938) BM25를 왜 섞나?
**A.** 정직한 수치이고, 그래서 그대로 게재했습니다 — 밀집임베딩은 이 작은 코퍼스의 하드네거티브를
벡터 단독으로 이미 구분하는데, BM25가 min-max 결합 구간에 약간의 노이즈를 더하고 그 하락은
리랭킹·질의확장이 회복시킵니다(최종 1.000). 그래도 BM25를 유지하는 이유는 밀집 모델이 약한
고유명사·코드 정확 매칭의 **보험**이기 때문입니다 — 코퍼스가 커져 임베딩이 못 본 용어가 늘수록
이 보험의 가치가 커집니다.

### Q35. Bi-Encoder와 Cross-Encoder 개념을 코드 어디에 구현했나?
**A.** 1차 하이브리드가 Bi-Encoder 감각(질의·문서를 각각 벡터화해 빠르게 넓게 회수), 2차 리랭커가
Cross-Encoder 감각(질의-청크를 함께 보고 정밀 재점수)입니다. 실무에선 2차를 실제 Cross-Encoder나
LLM 리랭커로 교체하며, 그 자리를 `HybridRetriever._rerank_score`로 남겼습니다.
섹션 타입 prior 같은 구조 신호는 Cross-Encoder 입력에 제목·섹션 메타를 넣는 형태로 그대로 이식됩니다.

### Q36. 검색 품질을 어떻게 개선해 왔나(오류 분석 루프)?
**A.** 실패 문항만 뽑아 진단하는 스크립트로 원인을 분류하고 각각 고쳤습니다 — ① 사전 결핍(구어 축
동의어 보강), ② 리랭커 신호 결함(섹션·제목 필드 분리), ③ 재가중으로 안 풀리는 잔여 실패는 신호
추가(섹션 타입 prior)로 해결해 Hit@1 0.867→0.967→1.000에 도달했습니다. **실패한 실험**(밀도 신호 —
대조 섹션이 용어를 반복해 HardNeg 악화)도 기록했습니다 — "왜 그 신호는 없나"에 수치로 답하고
같은 가설의 재시도 낭비를 막기 위해서입니다.

## D. 에이전트·Function Calling·멀티 백엔드 (Q37~Q48)

### Q37. LLM tool-use 루프는 어떻게 구현했나?
**A.** MCP `list_tools()`로 받은 스키마를 Anthropic tools 포맷으로 변환해 넘기고, `stop_reason`이
tool_use면 MCP로 호출→`tool_result` 되먹임을 반복하는 루프입니다(최대 6스텝 — 무한루프 방지).
도구가 실패해도 크래시하지 않고 `is_error=True`로 흡수해 모델이 다른 도구·인자로 스스로 재시도하게
합니다. 시스템 프롬프트는 "반드시 도구로 조회 후 근거 기반 답변"을 강제하며, 종료 시 답변은
검증 게이트를 거쳐 출처와 함께 반환됩니다.

### Q38. Agentic Workflow가 실제로 발현되는 예는?
**A.** "GMP 변경인데 뭘 준비하고 언제까지?" 같은 복합 질문에서 Claude가 한 루프 안에서
`search_regulations` → `get_submission_checklist` → `get_ra_deadlines`를 **연쇄 호출**해 결과를
종합합니다. 도구 선택은 docstring(사용 조건 명시)을 근거로 모델이 스스로 하며, 이 도구 선택
품질 자체를 `eval/plan_eval.py`로 따로 측정합니다. 미리 짠 파이프라인이 아니라 모델의 판단으로
도구 호출 계획이 구성되는 것이 Function Calling과의 차이입니다.

### Q39. abstention(환각 회피)은 어떻게 동작하나?
**A.** 두 신호 — 최상위 근거의 리랭커 점수(SCORE_FLOOR=0.19)와 질의 토큰의 근거 커버리지
(COVERAGE_FLOOR=0.28) — 가 **둘 다** 미달일 때만 "근거를 찾지 못했습니다"로 회피합니다.
AND인 이유: 구어체 정상 질문은 점수가 낮아도 커버리지가 남는데, OR면 이런 질문까지 과회피합니다.
문턱은 감이 아니라 범위내/범위밖 질문의 점수 분포를 실측해 마진 중앙에 놓았고, 근거 분포를
코드 주석에 남겨 리랭커 교체 시 재보정하게 했습니다(AbstentionAcc 1.000·OverAbstain 0.000).

### Q40. abstention에서 잡은 자기일관성 버그는?
**A.** 리랭커 개선 후 OverAbstain이 오히려 늘어난 증상의 원인이 **커버리지 신호가 원 질의 토큰만
보는 것**이었습니다 — 검색은 동의어 확장으로 정답을 찾는데 회피 판정만 원 질의 기준이라
"정답을 찾아 놓고 모른다고 답하는" 자기모순이었죠. 커버리지를 확장 질의 기준으로 고치고 분포를
재실측해 문턱을 다시 잡았습니다. 교훈은 "파이프라인은 부품이 아니라 결합된 시스템"이라는 것 —
리랭커가 바뀌면 문턱 재보정이 필수 절차이며, 이를 회귀 테스트로 박았습니다.

### Q41. 오프라인 규칙 라우터의 설계 원칙은?
**A.** **확신 있는 신호가 있을 때만 매칭하고, 미매칭이면 추측하지 않는 것**입니다. 케이스 질문은
케이스 마커(환자/복용 후)+사건 어휘(입원/쇼크)의 AND 조건으로 트리아지 도구로, 규정 질문은 검색으로
보냅니다. 체크리스트 카테고리를 확신 없이 기본 추측하면 도구의 에러 계약이 발동할 기회가 없어져
사용자가 엉뚱한 답을 자신 있게 받으므로, 미매칭은 지원 목록 안내+검색 폴백으로 처리합니다 —
안전장치를 만든 층 아래에서 그 장치를 우회하지 않는 것까지가 계약의 완성입니다.

### Q42. 멀티턴은 어떻게 처리하나?
**A.** 오프라인 모드도 짧은 후속질문("그럼 변경신고는?")을 직전 발화와 병합해 맥락을 유지합니다.
단, **이전 턴의 검색 근거는 이번 턴의 신뢰 소스로 이월하지 않습니다** — 이월하면 오래된 근거가
새 질문의 클레임을 지지하는 시간 오염이 생깁니다. 대신 질문의 전제 수치는 from_question 라벨로만
완화하되, 그 창도 직전 턴까지로 제한합니다 — 대화 전체를 누적하면 무관한 옛 수치가 이후 모든
환각을 완화 라벨링하기 때문입니다.

### Q43. 에이전트 백엔드가 3개인 이유는?
**A.** 같은 계약(검증 게이트 `_finalize`·MCP 도구·스텝 상한)을 지키는 **병렬 구현 3종** —
direct(anthropic SDK 직접 루프)·PydanticAI·LangGraph — 을 `AGENT_BACKEND` 환경변수로 교체·비교할
수 있게 했습니다. 공고의 요구 스택(PydanticAI·LangChain/LangGraph)을 실제 작동 코드로 증명하는
동시에, "프레임워크는 교체 가능한 껍데기이고 계약(검증·도구·안전장치)이 본체"라는 설계 주장을
구조로 보여줍니다.

### Q44. LangGraph 백엔드는 어떻게 구현했나?
**A.** 명시적 StateGraph로 agent 노드⇄ToolNode 순환을 구성하고, direct 백엔드의 6스텝 상한을
recursion_limit(왕복당 슈퍼스텝 환산)으로 대응시켰습니다. MCP 도구는 LangChain `StructuredTool`로
**무변환 래핑**해 같은 MCP 서버를 그대로 씁니다. GraphRecursionError는 direct의 스텝 상한 초과와
같은 계약(확정 실패 안내)으로 마감합니다 — 백엔드가 달라도 실패 방향이 같아야 하기 때문입니다.

### Q45. PydanticAI 백엔드는 어떻게 구현했나?
**A.** PydanticAI의 MCPToolset이 같은 `MCP_SERVER_URL`(HTTP)에 직결되어 도구 계층을 공유하고,
답변은 동일한 `_finalize` 검증 게이트를 통과합니다. 특기할 점은 search_web 처리입니다 — 명시
요청이 없는 턴에는 실행 관문에서 에러 계약으로 거부해(direct는 도구 목록에서 제외), 프레임워크가
달라도 "명시와 분리" 원칙이 같은 강도로 성립하게 했습니다.

### Q46. LLM API가 실패하면 오프라인 모드로 자동 전환하나?
**A.** 하지 않습니다 — **조용한 모드 전환은 또 하나의 조용한 실패 경로**이기 때문입니다.
키 오류(401)·네트워크 장애·잘못된 모델명이면 예외 타입을 포함한 명시적 실패 안내로 답합니다
(예외 메시지는 비에코 — 에코는 유출 경로). 자동 강등하면 사용자는 어느 모드의 답을 받았는지
모르게 되며, 이는 인지일 자동 정정 금지와 같은 철학입니다.

### Q47. grounded 신호는 무엇인가?
**A.** "성공한 도구 출력이 신뢰 소스로 확보되었는가"의 라벨입니다 — LLM 모드는 문턱 회피가 없는
대신 시스템 프롬프트의 도구 강제 + 사후 검증 게이트 + grounded 라벨이 근거 규율을 나눠 맡습니다.
모델이 도구 없이 답하는 것을 차단하지는 않되(차단은 유용한 안내까지 막음) grounded=False로
노출합니다. v7 전에는 이 값이 기본 True로 방치되어 출처 0건 답변이 근거 배지를 달고 나가던
'범위의 과확장' 결함이 있었고, 이를 수정했습니다.

### Q48. 인터넷 검색(search_web)은 왜 "명시와 분리"인가?
**A.** 사내 문서에서 못 찾은 질문을 조용히 웹으로 대신 답하면 abstention이 무력화되기 때문입니다 —
회피는 회피로 남기고, 웹 검색은 사용자가 명시적으로 요청한 턴에만 도구가 노출·허용됩니다.
결과는 `origin="web"`과 분리 고지가 박혀 전 계층(답변 🌐 표시·별도 필드·검증 from_web 라벨)에서
사내 근거와 구분되며, 사내 신뢰 소스로 승격되지 않습니다. 백엔드는 DuckDuckGo HTML 파싱 최소
구현으로, 실배포에선 사내 승인 검색 API로 봉합선만 교체합니다.

## E. MCP·FastMCP (Q49~Q58)

### Q49. 왜 MCP인가? 그냥 함수 호출하면 되지 않나?
**A.** 재사용성과 독립 진화 때문입니다 — MCP 규격으로 분리하면 한 번 만든 RA·PV 도구 서버를
Claude Desktop·Cursor·사내 다른 에이전트가 코드 수정 없이 재사용하고(N×M 통합→N+M),
모델 교체와 도구 확장이 서로 독립이 됩니다. 실제로 이 데모의 자체 에이전트와 Claude Desktop이
같은 서버의 도구를 호출하는 것을 시연했습니다. 도구를 에이전트 코드에 함수로 박았다면
불가능했을 확장성입니다.

### Q50. MCP 3대 primitive를 어떻게 구현했나?
**A.** **Tools 7종**(검색·마감일·체크리스트·PV 트리아지·ICSR 초안·문서 목록·웹 검색),
**Resource** `regulation://{doc_id}`(검색이 아닌 '원문 전체 열람'은 다른 접근 패턴), **Prompt**
`pv_case_intake`(케이스 처리 SOP 배포)입니다. 도구 함수 자체는 얇은 래퍼로 — 로직은
`src/rag/`·`src/pv/`·`src/ra/`에 위임하고 — 서버 계층은 인자 마스킹·스키마·docstring·에러 계약만
맡습니다.

### Q51. Function Calling과 MCP의 관계는?
**A.** Function Calling은 "모델이 도구를 호출하는 능력"(Anthropic tools 파라미터)이고, MCP는
"도구를 표준 규격으로 제공하는 프로토콜"입니다 — 층이 다릅니다. 이 데모는 MCP 서버의 도구
스키마를 `list_tools()`로 받아 Anthropic tools 포맷으로 변환해 둘을 연결합니다.
그래서 같은 도구가 자체 에이전트(Function Calling)와 Claude Desktop(MCP 클라이언트) 양쪽에서
동작합니다.

### Q52. 도구를 어떤 단위로 쪼갰나? assess와 draft를 왜 분리했나?
**A.** **사용자 의도 단위**입니다 — "언제까지 보고?"(판정 질문)와 "보고서 만들어줘"(산출물 요청)는
의도가 다르고, 합치면 판정 질문에도 긴 초안이 붙어 나옵니다. 도구는 의도 단위로 쪼개고 docstring에
용도 차이를 명시해야 LLM의 도구 선택 정확도가 올라갑니다. 대신 두 도구가 같은 판정 규칙(triage
모듈)을 공유해 결과 불일치가 없게 했으며, docstring·타입힌트가 곧 LLM에게 주는 사용설명서입니다.

### Q53. 도구의 에러 계약은 어떻게 설계했나?
**A.** "조용한 빈 결과 금지"입니다 — 미지원 카테고리·형식 오류·빈 질의에 빈 목록 대신
`{"error", "available": [...]}`/`{"error", "expected"}`를 반환합니다. available 목록은 에이전트의
**자가 정정 재료**가 되어 LLM이 올바른 인자로 재시도합니다. 후속 규율 두 가지 — ① 라우터가
확신 없는 기본값으로 도구를 부르면 이 계약이 무력화되므로 라우터는 추측하지 않고, ② 에러 문구에는
사용자 입력이 에코되므로 에러 응답은 검증의 신뢰 소스에서 통째로 제외합니다.

### Q54. Prompt를 왜 서버에 두나?
**A.** 도구만 배포하면 '올바른 사용 순서'가 클라이언트마다 제각각이 되기 때문입니다 —
`pv_case_intake`는 케이스 처리 SOP(assess→search→draft→누락 안내)를 서버가 배포해, 어느
클라이언트가 붙어도 같은 절차로 일하게 합니다. 조직의 업무 절차를 코드처럼 버전 관리해 배포하는
것이 MCP Prompts의 실질적 의미입니다. 프롬프트에 삽입되는 케이스 서술도 마스킹합니다 —
SOP가 PII 경계 절차만 빼고 배포되면 안 되기 때문입니다.

### Q55. Resource를 템플릿과 정적 리소스 두 벌로 등록한 이유는?
**A.** 클라이언트 UI의 실측 차이 때문입니다 — 템플릿(`regulation://{doc_id}`)은
resources/templates/list에만 잡혀 Claude Desktop의 첨부 메뉴(구체 URI 열거)에 나타나지 않습니다.
그래서 코퍼스 13종을 구체 URI의 정적 리소스로도 등록해, 열거·선택은 정적 리소스가,
파라미터 접근은 템플릿이 맡게 했습니다. 표준 스펙과 클라이언트 구현의 간극을 실측으로
확인하고 두 접근 경로를 병행한 사례입니다.

### Q56. MCP 서버의 실행 모드 두 가지는?
**A.** ① stdio(`python -m src.mcp_server.server`) — Claude Desktop·Cursor 연결용,
② HTTP 독립 서버(`--transport http --port 8001`) — 운영 기본값으로, 에이전트·API와 **별도
프로세스**에서 돌고 `MCP_SERVER_URL`로 원격 연결합니다(docker-compose의 mcp 서비스,
Render의 rapv-mcp). RAG 인덱스는 MCP 서버 프로세스가 소유하고 API는 상태를 조회만 하는
완전 분리 구조입니다.

### Q57. HTTP transport에서 stateless_http=True를 쓴 이유는?
**A.** 재배포 무중단 때문입니다 — 기본(stateful)은 프로토콜 세션 장부가 프로세스 메모리에 있어
재배포가 곧 전 세션 무효화이고, 세션을 들고 있던 Claude Desktop(mcp-remote)이 'Session not found'
404로 죽는 것을 실배포에서 실측했습니다. 이 서버는 서버발 기능(sampling·알림·구독)을 안 쓰는
순수 요청-응답이라 세션의 이점이 없고, 무세션이 곧 재배포 무중단입니다. 앱 수준 상태(RAG
인덱스·계기판)는 층이 달라 영향이 없습니다.

### Q58. MCP 서버를 공개 URL로 열 때의 보안은?
**A.** `MCP_AUTH_TOKEN` 설정 시 Bearer 토큰 검증(StaticTokenVerifier)이 걸리고, 클라이언트
(에이전트·preflight)는 자동 부착합니다. 핵심은 `MCP_REQUIRE_AUTH` **fail-closed 가드**입니다 —
켜면 preflight가 '토큰 없는 공개 서버' 상태로는 기동을 거부해, 나중에 토큰이 실수로 지워져도
무인증 공개 상태로 조용히 돌아가지 않습니다. `/health`는 인증 밖에 남깁니다(Render 헬스체크가
무토큰 호출 — 실측 확인).

## F. PV 도메인 워크플로 (Q59~Q70)

### Q59. 트리아지의 판정 규칙은?
**A.** REG-005 §2를 코드로 옮긴 결정론 규칙입니다 — 사망·생명위협은 지체 없이(D+0), 그 외 중대
기준(입원·장애·기형·의학적 중요) 충족은 인지일로부터 15일(역일) 이내 신속보고, 비중대는
정기보고(PSUR)입니다. 예상 여부를 판별 못 하면 '예상치 못한 사례'로 보수 적용합니다 —
기한을 놓치는 쪽보다 이르게 잡는 쪽이 안전한 실패이기 때문입니다. 모든 판정에 "최종 확정은
PV 담당자" caveat와 근거 규정 문단(basis)이 붙습니다.

### Q60. "중대성은 닫힌 목록 대조라 규칙으로 충분하다"는 주장의 한계는?
**A.** 2단으로 말해야 안전합니다 — 닫힌 것은 '기준 목록'이지 '입력'이 아닙니다. 자유 텍스트
서술을 기준에 매핑하는 앞단은 키워드 감지이고, 이 단은 **과탐 방향 보수**(부정문 "사망하지 않았다"도
중대 후보로) + 동음이의 결합형 축소 + 사람 확정 caveat로 설계했습니다. PV 트리아지에서 안전한
실패 방향은 과보고입니다 — 놓친 신속보고가 불필요한 검토 1건보다 훨씬 비쌉니다.
"그 대조의 입력도 자연어인데 인과성과 뭐가 다른가"에는 이 구분(기준의 인식론 vs 입력의 NLP)으로 답합니다.

### Q61. 사망 어휘 감지는 어떻게 설계했나?
**A.** 사망은 **미탐이 치명적인 축**(놓치면 D+0가 정기보고로 오라우팅)인데, 사망 어휘는 형태 규칙
하나로 안 덮이는 열린 집합(별세·소천·타계·영면…)입니다. 그래서 NFKC 같은 클래스 봉합이 아니라
**열거+recall 규율**로 정직하게 명명하고 넓게 잡되, 짧은 마커는 형태소 확정형으로 좁혔습니다 —
'급사'가 지급사유·공급사에, '별세'가 특별세에 부분 문자열로 오발화해 정상 케이스를 D+0로
오라우팅한 실측 때문입니다(v12). 잔여 tail은 문서화하고 근본 해결은 NER/사전 교체 지점입니다.

### Q62. '장애' 키워드의 동음이의 문제는?
**A.** 한국어 의무기록의 "위장 장애"·"수면장애"의 '장애'는 disorder(질환 분류)이지
disability(신체 장애)가 아닌데, 단독 매칭은 이를 전부 중대(15일 신속보고)로 밀어 올렸습니다(v8).
그래서 disability 의미가 확정되는 결합형("영구 장애"·"장애 판정"·"장애가 남", 실명·청력 상실)으로만
좁혔습니다. 과탐 보수가 원칙인 트리아지에서도, 의미가 다른 어휘의 과탐은 오라우팅이므로
좁히는 것이 맞습니다 — 보수 방향은 축마다 따로 판단합니다.

### Q63. 인지일(awareness_date) 입력 오류는 어떻게 처리하나?
**A.** 형식 오류는 오늘로 폴백하되 **시끄러운 caveat**를 붙입니다("실제 인지일로 재계산 필요") —
잘못된 기준일로 계산된 기한은 컴플라이언스 리스크인데 조용한 폴백이면 사용자가 신호를 못 받습니다.
형식은 맞지만 미래 날짜면 타당성 caveat를 따로 붙입니다 — 형식 검사만 하고 값 타당성을 안 보면
2027로 잘못 친 인지일이 기한을 1년 뒤로 조용히 밉니다. 단 자동 정정은 하지 않습니다 —
그것도 또 다른 조용한 폴백이기 때문입니다. caveat 속 원문 에코는 마스킹합니다(PII 우회로 차단).

### Q64. 인과성 평가는 왜 '판정'이 아니라 '제안+질문'인가?
**A.** 업무의 인식론적 성격이 다르기 때문입니다 — 중대성은 닫힌 목록과의 '대조'지만, 인과성은
임상 정보(중단/재투여 경과·병용약·기저질환)를 '종합 판단'하는 일이라 정보가 부족하면 답 자체가
없습니다. 그래서 WHO-UMC 판단 요소 4신호(시간적 선후·dechallenge·rechallenge·대체 원인)를 감지해
도달 가능한 등급을 **제안**하고, 서술에 없는 정보는 follow-up 질문으로 돌려줍니다(정보 없는 요소는
충족으로 안 침 — 등급은 아래로만). 실제 WHO-UMC는 6범주이고 데모는 5범주 근사임을 먼저 밝힙니다.

### Q65. 부정문("호전되지 않았다")은 어떻게 처리하나?
**A.** 열거가 아니라 **부정 어미 일반 규칙**입니다 — 긍정 어휘 매칭 직후 N자(절 경계 전) 이내의
부정 어미(않·없·아니·아닌)를 검사해, 부정이 확인되면 '판단 불가'가 아니라 반대 상태(반증)로
매핑합니다. 절 경계 처리도 정교화했습니다 — 쉼표를 넘으면 다음 절의 무관한 부정을 삼키고(v10),
줄바꿈은 양의적이라(용언 랩 vs 절 구분) 직후가 용언 연속이면 같은 절로 이어붙입니다(v12).
"열거식 봉합은 다음 반례에서 진다"는 교훈이 클래스 규칙으로 이어진 대표 사례입니다.

### Q66. 용어 코딩의 3계층 구조는?
**A.** ① 확정(`code_terms`) — 검수된 소사전 매칭만 자동 확정(정밀도 무관용), ② 후보
(`suggest_candidates`) — LLT 스타일 참조 테이블 매칭은 `needs_confirmation=True`로만 제시(사람
승인 후 1계층 승격 — 사전 성장의 운영 루프), ③ 미코딩 감지(`flag_uncoded_expressions`) — 어느
사전에도 없는 증상 서술은 존재만 표시(PT 없음)합니다. 이 구조로 코딩 실패가 '보고 불가' 오판으로
연쇄되지 않으면서(④요건은 확정∪후보∪감지), 모든 실패가 시끄러운 보완 요청으로 남습니다.

### Q67. 코딩 재현율 갭(0.792)을 사전 추가로 지우지 않은 이유는?
**A.** 라벨을 보고 사전을 채우면 지표는 1.000이 되지만 '검수된 사전'이라는 1계층의 신뢰 모델이
무너지고, 실무에서 반복될 문제(사전엔 언제나 롱테일이 있다)를 데모에서만 지우는 것이기 때문입니다.
대신 실패를 계층으로 분해했고, 심층 롱테일 케이스를 평가셋에 오히려 추가해 갭을 유지했습니다.
개선의 실체는 재현율 숫자가 아니라 **실패의 형태**입니다 — '조용한 보고 불가 오판'이 '시끄러운
확정 요청+올바른 보고 가능 판정'(ReportableAcc 1.000)으로 바뀌었습니다.

### Q68. ICSR 초안 도구에서 요건 검증이 초안 생성보다 먼저인 이유는?
**A.** ICH E2D 4요소(식별 가능한 환자·보고자·의심약·이상사례)를 못 갖춘 케이스는 규제상 '유효한
보고'가 아니라서, 요건 검증 없이 초안만 만들면 미완성 케이스가 그럴듯한 문서로 포장되는 게 더
위험합니다. 그래서 도구의 1차 산출물은 문서가 아니라 "보고 가능한 상태인가"라는 상태 판정이며,
미충족이면 `reportable=False` + "⛔ 정보 보완 필요" 헤더가 최상단에 붙은 초안 + 빠진 항목·보완
질문을 병기해 반환합니다 — 미완성을 시끄럽게 표시하는 설계입니다.

### Q69. PII 마스킹과 '식별 가능한 환자' 요건은 모순 아닌가?
**A.** 아닙니다 — 요건의 본질은 '환자를 특정할 정보가 **존재**하는가'이지 원문 값이 아닙니다.
마스킹은 값을 지우되 존재 신호(`[이름]님`, `환자번호 [번호]`, "45세 남성")는 남기므로,
외부 API 경계에서는 값을 감추고 요건 판정은 신호로 하는 것으로 양립합니다.
마스킹된 케이스도 환자 요건이 충족으로 판정됨을 테스트로 보증하며, 마스킹 멱등성(이중 마스킹
금지)이 이 판정의 전제 조건이라 불변식 테스트로 고정했습니다.

### Q70. 의심 의약품은 어떻게 감지하나? 오탐은?
**A.** "OO정/캡슐 + 복용/투여"처럼 **노출(exposure) 맥락이 따라올 때만** 정규식이 매칭됩니다 —
'규정·판정·일정' 같은 '-정'으로 끝나는 일반 명사의 오탐을 막는 lookahead 설계입니다.
그래도 놓치는 경우(성분명만 언급)를 위해 `suspected_drug` 인자를 열어뒀고, 감지 실패는
'보완 필요'로 정직하게 표시합니다 — 조용히 틀리는 것보다 시끄럽게 빠뜨리는 것이 컴플라이언스
도구의 올바른 실패 방향입니다.

## G. PII·보안 (Q71~Q78)

### Q71. PII 마스킹이 2겹인 이유는?
**A.** "입구에서 막으면 이후 전부 안전"이라는 명제에는 '모든 입력이 그 입구를 지난다'는 숨은
전제가 있는데, MCP 서버는 stdio로 단독 실행될 수 있어(Claude Desktop 직결) 도구 인자가 에이전트
입구를 **거치지 않고** 들어옵니다. 그래서 에이전트 입구(메시지·이력)와 MCP 도구 계층(전 도구·
Prompt의 모든 자유 텍스트 인자 — 검색 query·필터 인자 포함)의 2겹입니다. PV 도구 2종만 마스킹하던
초기 상태는 '범위의 과확장'으로 판정해 전 도구로 넓혔습니다(v7) — 경계 주장은 우회 경로까지
검사해야 완성됩니다.

### Q72. 마스킹 정규식에서 \b 대신 룩어라운드를 쓰는 이유는?
**A.** 한글이 `\w`로 취급되어 "연락처는 010-…-5678로", "주민번호는 …입니다"처럼 조사·명사가
직결된(한국어에서 가장 흔한) 표기에서 `\b` 경계가 성립하지 않아 통째로 유출됐기 때문입니다(v6).
숫자 룩어라운드 `(?<!\d)…(?!\d)`로 전환했고, preflight PII 자가 테스트가 한글 직결 표기를 심어
기동 전에 확인합니다. 이 발견의 메타 교훈은 **교훈의 전파 감사**입니다 — 검증기의 날짜 추출이
먼저 배운 교훈이 마스킹 계층에 전파되지 않았던 비대칭 자체가 사각지대였습니다.

### Q73. 주민번호·전화번호 패턴의 설계 원칙은?
**A.** "비대칭은 곧 우회로"입니다 — 구분자 없는 표기·점 구분·en-dash·공백 패딩·국제표기(+82)·
괄호 지역번호까지, 한 패턴이 받는 표기를 다른 패턴이 못 받으면 그만큼이 유출 경로라 어휘를
동형으로 맞췄습니다. 주민번호 성별코드는 [1-8]입니다 — [1-4]로 좁히면 외국인등록번호(5~8)가
통째로 통과합니다. 방향 원칙은 "마스킹은 과탐이 미탐보다 싸다" — 오탐은 가려질 뿐이지만
미탐은 유출입니다.

### Q74. 이름 마스킹의 한계는?
**A.** 호칭(님/씨)이 붙은 이름만 잡는 경량 근사이며, 정규식으로 자유 서술 속 이름 전부를 잡을 수
없음을 명시했습니다 — 실무 교체 지점은 NER 기반 비식별화(Presidio 등)입니다. 오탐은 스톱리스트
(직함·역할 일반명사)로 막되, 친족·존칭 호칭어의 과마스킹은 **의도적으로 더 봉합하지 않습니다** —
열거식 스톱리스트 확장은 다음 반례에서 지는 패턴이고, 방향이 과탐(유출 아님)이라 NER 교체가
근본 해결이기 때문입니다. 스톱리스트에 남긴 항목은 '보호자'처럼 실제 오판(보고자 신호 소실)을
유발한 최소 집합입니다.

### Q75. NFKC 정규화는 왜 넣었나?
**A.** 전각 숫자("０１０－…") 표기의 주민번호·전화가 통째로 유출됐기 때문입니다 — `\d`는 전각을
매칭하지만 성별코드 [1-8] 같은 ASCII 앵커는 못 받는 간극이 있었고, 엑셀·한글 붙여넣기에서 전각
혼입은 실제로 흔합니다(v11). 진입부 NFKC 폴딩은 이 표기 축을 열거가 아니라 **클래스 차원**에서
봉합하는 사례입니다 — v12 재감사에서 "진짜 클래스 봉합"으로 인정된 것이 NFKC 하나였다는 점도
정직하게 기록했습니다.

### Q76. 대화 이력의 블록 리스트 표기 결함이란?
**A.** anthropic 대화 이력의 content는 문자열만이 아니라 블록 리스트(`content=[{"type":"text",…}]`)
로도 들어오는데, 이력 마스킹이 문자열 표기에서만 성립해 블록 표기 속 개인정보가 외부 LLM API로
그대로 나가는 경로였습니다(v7). 블록 표기 마스킹으로 봉합하고 preflight PII 자가 테스트에
블록 표기 프로브를 심어 고정했습니다. "X를 지원한다"는 주장은 모든 모드·모든 표기에서 참인지
물어야 한다는 v7 렌즈의 대표 사례입니다.

### Q77. 마스킹 멱등성이 왜 불변식인가?
**A.** `redact(redact(x)) == redact(x)`가 깨지면 이중 마스킹이 존재 신호(`[이름]님`)를 파괴해
최소보고요건의 '식별 가능한 환자' 판정이 무너지기 때문입니다 — 멱등성은 미관이 아니라 **요건
판정의 전제 조건**입니다. 고정 시드 fuzz 합성기(60케이스)로 어떤 입력 조합에서도 이 성질이
유지됨을 검증하며, 같은 하네스가 PII 비유출(도구 응답 JSON 전체에 원문 PII 부재)도 함께
성질로 고정합니다.

### Q78. 마스킹하면 답변 품질이 떨어지지 않나?
**A.** 떨어지지 않습니다 — 규제문서 검색에 PII 토큰은 어차피 노이즈라 검색 품질에 영향이 없고,
트리아지 판정도 증상·경과 어휘로 하지 이름·연락처를 쓰지 않습니다. '마스킹 후에도 판정·인용이
동일함'을 테스트로 보증합니다. 응답에는 유형·건수만 남기고 원 값은 어디에도 저장하지 않는
원문 비보존 원칙이라, 로그·트레이스·감사 기록 전 경로가 자동으로 안전해집니다.

## H. 답변 사후 검증 게이트·신뢰성 (Q79~Q88)

### Q79. 평가가 전부 1.000인데 왜 또 런타임 검증 게이트인가?
**A.** **평가는 오프라인 표본 측정**이라 다음 요청의 답변을 보증하지 않기 때문입니다 — 특히 LLM
답변은 매번 새로 생성되므로 근거는 "15일"인데 답변이 "30일"로 나오는 생성 오류를 평가셋은 못
막습니다. 그래서 **모든 응답**이 수치·단위·날짜·방향 한정어·날짜 역할을 근거와 대조하는 게이트를
통과합니다. abstention과의 차이는 시점입니다 — abstention은 생성 전("근거 부족하니 안 답함"),
게이트는 생성 후("답했는데 그 수치가 정말 근거에 있나")라 서로 대체하지 못합니다.

### Q80. 신뢰 소스는 어떻게 정의했나?
**A.** **검색 근거 ∪ 결정론적 도구 출력 − 입력 에코(query·as_of) − 에러 계약 응답**입니다.
도구가 계산한 값(인지일+15일=마감일)은 근거 원문에 없어도 테스트로 검증된 결정론이라 포함하고
(빼면 오탐→alert fatigue), 도구가 에코하는 사용자 입력은 제외합니다 — 포함하면 사용자의 틀린
전제에 모델이 맞장구쳐도 통과합니다(sycophancy 구멍). 에러 응답도 통째로 제외합니다 — 에러
문구에 입력이 에코되어 필드 단위 제거로는 승격 경로를 못 막기 때문입니다.

### Q81. 2계층 신뢰 소스와 from_case 라벨은 왜 필요한가?
**A.** "케이스는 사실이다"가 "케이스 수치는 규정 클레임의 근거다"로 승격되는 논리적 비약을 막기
위해서입니다 — 케이스의 "30일간 복용"이 답변의 "보고 기한 30일"을 지지하는 조용한 통과가
그 구멍입니다. 케이스 재서술은 정당하므로 경고하면 오탐이고, 침묵하면 은폐라, 케이스 계층에서만
지지되는 클레임은 `from_case` 라벨로 노출해 '재서술 vs 왜곡'의 판단을 사람에게 넘깁니다.
이 2계층은 축마다 일관해야 하며, 방향·역할 충돌의 판정 기준은 strict 계층입니다.

### Q82. 방향 한정어("이내"↔"이후") 검증은 어떻게 가능해졌나?
**A.** 처음엔 "관계 왜곡은 LLM judge의 몫"으로 선을 그었는데, 그 문장을 재심사하니 방향 한정어는
자연어 전체가 아니라 **닫힌 어휘 집합**(이내·이하·미만·까지/이상·이후·초과)이라 결정론으로 잡을 수
있었습니다 — '기계 검증 가능'의 경계 설정 자체에 비약이 있던 것입니다(v2). 기간·날짜("~까지")·
고유어("보름 이후") 전 표기에 대칭 적용합니다 — 일부 표기에만 있으면 같은 왜곡이 표기에 따라
한쪽만 잡히는 비대칭이 됩니다. 근거에 한정어가 없으면 판정하지 않습니다(보수적 — 오탐 방지).

### Q83. 날짜 역할 스왑 검증이란?
**A.** 도구 출력에 날짜가 여러 개면(인지일·마감일) 답변이 두 날짜의 역할을 맞바꿔도 각 날짜가
실존하므로 존재 대조는 **정의상 통과**합니다 — 기한을 실제보다 앞뒤로 읽게 만드는 가장 위험한
오류입니다. 해법은 닫힌 집합 두 개의 곱입니다 — 답변에서 역할 키워드(기한/마감·인지일)에 직접
붙은 날짜만 도구의 역할 라벨(deadline_date·awareness_date)과 대조합니다. 라벨이 없으면 판단하지
않는 보수 설계이고, DateRoleSwapDetection 축을 메타 평가에 신설해 탐지를 핀으로 만들었습니다.

### Q84. 날짜 표기 정규화는 왜 하나?
**A.** 오탐도 결함이기 때문입니다 — 정규화 없이는 올바른 답변이 표기 차이("2026년 7월 25일" vs
ISO)로 '미확인' 오탐을 받고, alert fatigue가 검증 계층을 죽입니다. 한국어 표기·연도 없는 부분
표기("7월 25일" — --MM-DD 접미 대조)·연도 단독 표기("2025년")를 동치 대조하고, 날짜의 '25일'
성분이 기간 클레임으로 오추출되는 것도 정규식 경계로 차단합니다. 환산이 아니라 **표기 정규화**라
단위 엄격성("15일"→"약 2주"는 여전히 실패)과 충돌하지 않습니다.

### Q85. 검증 실패 시 왜 차단하지 않고 경고만 붙이나?
**A.** 검증기 자신도 오탐 가능성이 있기 때문입니다(정당한 패러프레이즈 등) — 오탐 있는 검증기로
자동 차단하면 정당한 답변이 죽고, 검증을 끄면 환각이 샙니다. 그래서 '시끄러운 경고+사람 확정'이며,
경고는 본문·API `verification` 필드·UI 배지 세 곳에 노출해 무시할 수 없게 했습니다.
지원된 클레임에는 근거 위치 스니펫(evidence)을 붙여 사람의 원문 대조를 빠르게 합니다 —
원칙은 '사람의 최종 확정을 빠르게'이지 자동화가 아닙니다.

### Q86. 폐지본 인용 감지에서 "스위치의 면적" 문제란?
**A.** 이력 조회에서 폐지본 인용은 결함이 아니라 목적이라 경고를 꺼야 하는데, 그 면제를 응답
전역 bool로 구현하면 같은 턴의 현행 검색에 상류 결함으로 섞여 든 폐지본 인용까지 경고가 꺼져
이력 턴 동안 버전 축이 통째로 무장해제됩니다(v4 발견). 그래서 면제의 면적을 **이력 검색이 실제로
반환한 doc_id 집합 단위**로 좁혔습니다. 원칙 — 안전장치를 끄는 스위치는 발동 조건과 발동 범위
모두, 근거가 성립하는 만큼만 열려야 합니다.

### Q87. "그 검증기는 누가 검증하나"에 대한 답은?
**A.** **메타모픽 평가**입니다 — 정상 답변에 결정론적 변조(seeded corruption)를 가해 오류를
합성하고 탐지율을 잽니다: 교차문서 치환·오프셋·방향 뒤집기·고유어 치환·날짜 시프트·역할 스왑 등
탐지 축과 오탐 감시 축(CleanPassRate·ParaphrasePassRate)을 함께 둡니다(현재 9축 93건, 전 지표
Wilson CI). 탐지율 1.000은 새 발견이 아니라 **회귀 고정 핀**이며, pytest 가드가 탐지율·오탐률·
표본 수 하한을 CI 실패로 강제합니다 — '측정이 존재한다'와 '측정이 지킨다'는 다르기 때문입니다.

### Q88. LLM judge 2차 검증은 어떤 역할인가?
**A.** 결정론 게이트가 스스로 경계로 선언한 것 — 부정문 뒤집기·주어 바꿔치기·수치 없는 의미
왜곡 — 만 보는 opt-in(기본 off) 확률 계층입니다. 켜는 것은 비용(전 응답 유료 콜)과 비결정론을
받아들이는 명시적 결정이라 기본 비활성이고, 판정 모델(JUDGE_MODEL, 저비용)을 생성 모델과 분리해
self-critique 순환을 부분 완화합니다. 판정은 비차단(경고 부착만)이고 결정론 축은 중복 판정하지
않으며, API 실패는 `status="unavailable"`로 가시화합니다 — '안 돌았다'와 '이상 없음'을 구분합니다.

## I. 평가·테스트·CI·preflight (Q89~Q96)

### Q89. 평가 체계 전체를 요약하면?
**A.** 세 겹입니다 — ① pytest 380케이스(판정 로직·마스킹·불변식, 코드 수준 고정), ② 품질 평가
7종(`evaluate` 검색·`sweep` 하이퍼파라미터/ablation·`faithfulness` 신뢰성·`pv_eval` PV 22라벨·
`verify_eval` 게이트 메타모픽·`robustness_eval` 견고성·`plan_eval` 도구 선택 + opt-in `judge_eval`),
③ preflight 28건(배포 전 점검, 실패 시 기동 차단). 세 단계 모두 코드 수정·배포 때마다 실행되며
CI가 매 푸시마다 강제합니다. 소표본 지표엔 항상 Wilson 95% CI를 병기합니다.

### Q90. 개발셋 1.000과 홀드아웃의 관계는? 홀드아웃 0.833→1.000은 오염 아닌가?
**A.** 32문항은 오류 분석에 쓴 개발셋이라 그 위의 1.000은 일반화가 아니라 **개발셋 포화**이고,
일반화 근사는 튜닝에 일절 안 쓴 홀드아웃 6문항으로 따로 봅니다. 첫 측정 0.833의 유일 실패는
파 보니 검색기 결함이 아니라 **복수 정답 문항의 라벨 모호성**이었고(REG-011 §3도 동등 정답),
`accept_doc_ids`로 정답 집합만 교정했습니다 — 검색기 튜닝은 하지 않았으므로 홀드아웃 규율은
유지됩니다. 교정 후 1.000도 n=6·CI 하한 0.610이라 일반화 보장으로 읽지 않고 교정 이력을 병기합니다.

### Q91. 왜 Wilson 신뢰구간인가?
**A.** ① 이항 비율 전용 폐쇄형 공식이라 난수 없이 **결정론적** — CI 로그가 매 실행 동일해 회귀
비교가 되고(부트스트랩은 아님), ② 소표본·극단 비율(1.000/0.000)에서 Wald 근사처럼 구간이 0폭으로
붕괴하지 않습니다 — 정확히 이 프로젝트가 있는 영역입니다. 해석 규율도 함께 둡니다 — 두 구간이
크게 겹치면 '개선'이 아니라 '구분 불가'로 읽고, 1.000 [0.893, 1.000]은 '완벽'이 아니라
'이 표본에서 실패 관측 0'으로 읽습니다.

### Q92. 견고성(robustness) 평가는 무엇을 재나?
**A.** 실사용 입력의 지저분함을 견디는지입니다 — 오타·구어체 등 섭동 128건에서 0.969,
프롬프트 주입 공격 9종에서 1.000 방어를 측정했습니다(`eval/robustness_dataset.json`).
주입 방어가 구조적인 이유는 답변이 자유 생성이 아니라 근거 강제+검증 게이트를 거치기 때문입니다.
평가셋 후보는 LLM으로 생성하되 리뷰 게이트를 구조로 강제해(generate_eval) 셋 자체의 품질도
관리합니다.

### Q93. 테스트 380케이스는 어떻게 구성되나?
**A.** 예시 기반 테스트(특정 판정의 정확성)와 **불변식 테스트**(어떤 입력 조합에서도 깨지면 안
되는 성질)의 이중 구조입니다. 불변식은 고정 시드 fuzz 60케이스로 7성질을 고정합니다 — 결정론,
닫힌 출력 집합(기한은 0·15·None 밖으로 절대 안 나감), 날짜 일관성, 마스킹 멱등성, PII 비유출,
코딩 계층 배타성, 검증기 자기일관성(`verify_answer(x,[x]).ok`). 시드를 고정하는 이유는 재현
가능성입니다 — CI에서 시드가 매번 다르면 실패가 재현이 안 돼 회귀 테스트가 아니라 복권입니다.

### Q94. preflight는 무엇을 검사하고 테스트와 어떻게 다른가?
**A.** 결정론 점검 4그룹입니다 — ① 설정 불변식(값은 유효해도 조합이 모순), ② 코퍼스 무결성
(frontmatter 누락·doc_id 중복·폐지 체인 단절·시행일 단조성), ③ 업무 데이터 스키마(마감일 전건
과거 같은 값 타당성 포함), ④ 스모크 canary + 안전장치 자가 테스트. 테스트와의 차이는 검사
대상·시점입니다 — 테스트는 코드를 리포 시점에, preflight는 **배포 환경의 데이터·설정**을 기동
시점에 검증합니다. 고객사에서 문서·환경변수가 바뀌는 순간 pytest는 아무것도 보장하지 않습니다.
단, 수동 uvicorn 실행은 게이트 밖임을 가이드에 명시했습니다(숨은 전제의 문서화).

### Q95. "안전장치 자가 테스트"의 대칭 원칙이란?
**A.** 고장난 안전장치를 단 채 배포되는 것은 안전장치가 없는 것보다 나쁘므로(있다고 믿게 만듦),
preflight가 검증 게이트와 PII 마스킹 자신을 기동 전에 검사합니다 — 심은 오류가 '기대한 바로 그
축에' 걸리는가, 심은 개인정보가 실제로 지워지는가. 이 원칙은 대칭적으로 적용합니다 — 장치 간
(게이트만 검사하면 마스킹은 고장난 채 배포 가능), 그리고 한 장치의 내부 축 간(수치 축만 심으면
방향·역할·버전 축은 고장난 채 배포 가능). 축 목록과 자가 테스트 커버리지가 어긋나면 pytest
메타 테스트가 실패해, 새 축 추가 시 자가 테스트가 구조적으로 강제됩니다.

### Q96. CI는 어떻게 구성했나?
**A.** 저장소 루트 `.github/workflows/ci.yml`(GitHub Actions는 루트만 인식, working-directory로
project 실행)에서 매 푸시마다 preflight + pytest + 평가 회귀(검색·신뢰성·PV·검증기에 계획·견고성
추가)를 실행합니다. 핵심 교훈은 **측정과 강제의 분리**입니다 — 초기 CI는 평가 스크립트를 실행만
하고 exit 0이라 "탐지율은 회귀 핀"이라는 주장이 강제되지 않았고, pytest 가드(탐지율·오탐률·표본
수 하한 단언)를 추가해 CI 실패로 강제했습니다. 리포의 데이터 변경도 같은 게이트를 지납니다.

## J. 운영·배포·종합 (Q97~Q100)

### Q97. 관측성은 어떻게 구현했나?
**A.** 요청 1건(Trace) 안에 도구·LLM 스텝 단위 Span(이름·ms·성패)을 쌓고 구조화(JSON) 로그를
남깁니다 — OpenTelemetry/LangSmith 개념의 무의존성 구현입니다. 계기판 자체도 검증 대상입니다 —
총 지연은 최상위 span의 wall-clock으로 계산하고(스텝 합산은 시간을 이중 계산해 ~2배 왜곡),
게이트 경고율은 분모를 명시한 `warn_rate_checked`(클레임 있던 응답만)를 병기하며, 경고에 안
잡히는 이동은 `case_labeled` 추이로 봅니다. "틀린 계기판은 계기판이 없는 것보다 나쁘다"가 원칙입니다.

### Q98. 배포 구성은?
**A.** `run.sh`(venv+의존성+preflight+서버), docker-compose(mcp·api 2서비스 분리), Render
(render.yaml — rapv-mcp와 web 서비스, 실서비스 URL 운영)입니다. MCP 서버는 별도 프로세스
(포트 8001)로 완전 분리되어 API는 `MCP_SERVER_URL`로 연결하며, Render의 fromService 주입은
host 속성만 신뢰합니다 — hostport/port는 포트 감지에 의존해 첫 sync에 빈 값이 들어오는 것을
실배포에서 확인했기 때문입니다. preflight가 role별로 기동 전 게이트를 겸합니다.

### Q99. 실서비스로 가려면 무엇부터 바꾸나?
**A.** 임베더(상용/대형 밀집 임베딩 — VoyageEmbedder가 API 경로 증명), 리랭커(실제 Cross-Encoder),
벡터스토어(pgvector/Qdrant), PII(NER 기반 Presidio), 코딩 사전(MedDRA 본체 라이선스), 문서
인제스트(PDF/HWP 상용 파서 — `scripts/ingest_pdf.py`가 경로 증명), ICSR(E2B(R3) XML 생성),
인증·권한(SSO) 순입니다. 전부 이미 교체 지점이 인터페이스로 잡혀 있어, 코퍼스·라벨을 실데이터로
바꾸면 같은 평가 하네스가 품질을 재측정합니다.

### Q100. 이 프로젝트에서 가장 자랑하고 싶은 설계 하나는?
**A.** **실패 방향의 설계**입니다 — 어떤 실패도 크래시나 조용한 오답이 아니라 '설명되는 축소
동작'이 되게 만든 것: 빈 결과 대신 에러 계약, 폴백엔 caveat, 판정 불가면 보수 적용+사람에게 질문,
검증 실패는 경고 부착, 배포 전 결함은 기동 차단. 그리고 그 안전장치들 자신을 다시 검사 대상에
올렸습니다(자가 테스트·메타 테스트·계기판의 계기판). 규제 도메인에서 신뢰는 정확도 수치가 아니라
"틀릴 때 어떻게 틀리는가"에서 나온다고 생각하고, 그 원칙을 시스템 전 층위에 일관되게 적용했습니다.
